## 2. 得到大脑默认能力假设

**核心前提（务必遵守）：默认得到大脑读不了网页链接。**

- 不要只给 GitHub URL 或任意网页链接就要求执行任务。
- 如果必须给链接，必须**同时**提供：本地文件路径、关键内容摘录、任务说明。
- 所有关键输入应尽量以文本 / Markdown / DOCX / JSON / CSV 的形式**直接提供正文**，而不是只给链接。
- 如果让它读仓库，必须告诉它：先读哪些文件、按什么顺序读、哪些文件**不要碰**。
- 链接读取失败时，不要基于 URL 猜内容，必须要求转存正文后再做。

## 3. 得到大脑每次任务前必须读取的主线资产

按以下顺序读取（目录型资产读其入口或索引，不要盲目全量）：

1. `README.md` — 项目总览、目录结构、阶段记录。
2. `docs/getbrain-handoff-20260708.md` — 交回得到大脑的状态交接说明（当前状态、主线资产、使用原则、推荐任务）。
3. `docs/machine_readable_data_plan.md` — P1 机器可读化设计说明（数据范围、schema 约定）。
4. `统一函数总表/` — **最新函数表**。碰撞以它为准。
5. `统一案例总表/` — **最新案例表**。碰撞以它为准。
6. `data/` — P1 七类机器可读数据（csv+json）。
7. `data/schemas/` — 上述数据的 JSON schema（校验用）。
8. `tools/validate_data.py` — P1 数据校验器（碰撞前必跑）。
9. `outputs/audit/` — 历史审计记录（差异审计、MF 补入审计、v0.2/P1 审计等），用于理解既有决策。

**重要**：碰撞任务以 `统一函数总表/` 和 `统一案例总表/` 为「最新两张表」，**不再以任何临时仓库为准**。

## 4. 碰撞任务标准输入格式

每次碰撞任务必须给出下列固定模板（缺项视为输入不完整，应先补齐再执行）：

```
任务名称：
碰撞对象：
输入材料：
使用函数范围：
使用案例范围：
是否使用 P1 机器数据：
输出要求：
不得做的事：
保存位置：
```

说明：

- **输入材料必须贴正文或给本地文件路径**。如果只有网页链接，必须先转存为本地文本再碰撞（见第 10 节）。
- **函数范围默认全量**（即 `统一函数总表/` 全部条目）；除非任务明确限定某层/某类。
- **案例范围默认全量**（即 `统一案例总表/` 全部条目）；除非任务明确限定。
- **P1 数据默认可辅助索引**，但不得替代正式两张表，只能作为检索/交叉参考。

## 5. 碰撞执行流程

详细步骤（按顺序执行）：

1. 读取任务说明（含第 4 节模板内容）。
2. 确认输入是否完整；不完整则停止并要求补齐。
3. 运行或要求运行 `python3 tools/validate_data.py`，确认 P1 数据有效。
4. 读取最新函数表（`统一函数总表/`）。
5. 读取最新案例表（`统一案例总表/`）。
6. 读取 P1 机器数据（`data/`）。
7. 对碰撞对象做概念拆解（提取可判定结构）。
8. 与函数表碰撞（找同构、缺口、可合并项）。
9. 与案例表碰撞（找对应案例、反例、支撑）。
10. 找出**新增函数候选**。
11. 找出**新增案例候选**。
12. 找出**新增注释候选**。
13. 找出**扩展注释候选**（对已有条目的补充，不是新条目）。
14. 找出**不采纳项**（附理由）。
15. 输出结构化报告（按第 6 节五类分栏）。
16. 说明哪些内容需要回填两张表（按第 9 节规则）。

## 6. 碰撞输出必须分五类

固定为以下五类，每一类用对应字段输出：

### 6.1 新增函数

字段：

- 候选编号
- 函数名称
- 函数内容
- 函数层级
- 来源材料
- 关联案例
- 与现有函数差异
- 是否建议入表
- 理由

### 6.2 新增案例

字段：

- 候选编号
- 案例名称
- 案例内容
- 对应函数
- 来源材料
- 关键发现
- 是否建议入表
- 理由

### 6.3 新增注释

字段：

- 对应函数或案例
- 注释内容
- 注释类型
- 来源材料
- 是否建议入表

### 6.4 扩展注释

字段：

- 对应旧条目
- 扩展内容
- 为什么不是新增条目
- 是否建议更新

### 6.5 不采纳项

字段：

- 内容
- 不采纳理由
- 可能风险
- 是否需要以后复查

## 7. 碰撞完成后如何保存笔记

**重点：碰撞完成后，不要只在聊天里输出，必须保存为文件。**

建议保存位置：

- 碰撞类：`outputs/collisions/`
- 得到笔记来源类：`outputs/getbrain/`
- 审计类：`outputs/audit/`

文件命名规则：

```
YYYYMMDD-任务名-collision-report.md
YYYYMMDD-任务名-new-functions.md
YYYYMMDD-任务名-new-cases.md
YYYYMMDD-任务名-notes.md
YYYYMMDD-任务名-rejected.md
```

每次碰撞至少保存：

1. 完整碰撞报告；
2. 新增函数候选表；
3. 新增案例候选表；
4. 注释与扩展注释；
5. 不采纳项；
6. 回填建议；
7. 本次输入材料快照或来源说明。

## 8. 保存笔记的内容格式

每份笔记必须包含：

- 任务时间
- 输入来源
- 碰撞对象
- 使用的函数表版本
- 使用的案例表版本
- 是否使用 P1 数据
- 核心结论
- 新增内容
- 不采纳内容
- 待人工复核内容
- 下一步建议

**说明**：如果函数表版本无法确认，写「版本待确认」，不能假装确认。

## 9. 回填两张表的规则

- 不允许直接覆盖正式两张表。
- 先生成新增候选（第 6 节五类）。
- 再与现有两张表查重（编号、标题、语义）。
- 只回填通过查重的增量。
- 回填必须保留来源（来源材料字段）。
- 回填后必须生成审计记录（存入 `outputs/audit/`）。
- 回填后运行校验或至少做编号检查（不出现重复/跳号/冲突）。
- 不确定的内容进入 `pending`，不强行入表。

## 10. 网页链接处理规则

**默认得到大脑读不了网页链接。** 如果输入是网页链接：

1. 先尝试读取。
2. 如果失败，要求用户或 Agent 转存正文。
3. 正文保存到 `outputs/sources/`。
4. 再以本地正文文件为输入。
5. 碰撞报告中记录原始 URL 和本地快照路径。
6. **不得基于无法读取的链接编造内容**。
