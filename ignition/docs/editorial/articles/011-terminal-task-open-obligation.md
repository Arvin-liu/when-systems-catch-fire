# 一个系统如何在停止时仍然诚实：把开放义务从任务生命周期里拆出来

> 任务可以结束，义务可以继续；真正困难的是让这两个判断彼此可见、互不冒充。

## 最容易被误解的一句“完成了”

一个项目到了最后，常会遇到一句不舒服的话：这轮工作已经做完了，但还有一件重要的事没有做完。

如果只能在“完成”和“未完成”之间选一个，团队通常会有三种反应。有人坚持不许关单，于是任务永远停在运行中；有人为了让看板干净，直接把未完成的事从当前项目里抹掉；还有人把它写成一个模糊的“基本完成”，让读者自己猜剩下的到底是什么。三种写法都不诚实：第一种把未来责任误写成当前任务的生命，第二种丢掉责任，第三种把两种状态压成了一句漂亮但不可操作的话。

Task142 处理的正是这个窄而要命的工程问题。它的正式任务范围已经走完，状态是 `COMPLETED_WITH_OPEN_OBLIGATIONS`；与此同时，`LIVE_EXTERNAL_INVOCATION` 仍然是一个独立的开放义务。历史上有六次 attempt，validated completion 仍为零，未协调的次数为零，两个观测仍是不完整的。于是正确的记录不是“系统已经完成外部执行”，也不是“Task142 仍在运行”，而是：这项任务的范围结束了，另一条义务的生命周期没有结束。

这不是给“不够成功”找一个新标签，而是在修复这个仓库里“谁还活着”的判断。

## 两只时钟，而不是一个总开关

把问题说得更直白一点：任务和义务看的是两只不同的时钟。

第一只时钟问：这轮被明确承诺的工作，是否已经完成？它关注范围、交付物、预先声明的门槛和本轮的终态。第二只时钟问：一项需要未来继续处理的责任，是否已经被满足、撤回、转交或明确停放？它关注开放条件、历史证据、重试资格和下一次动作。

两只时钟有时会同时停下，有时不会。一个部署任务可能结束，但上线后的监测义务才刚开始；一次资料整理可以交付，但一条外部核验仍需等待；一个研究阶段可以收口，但复现或伦理审查还没有完成。把第二只时钟硬塞进第一只时钟，任务就会因为未来而永远不能结束。反过来，把第一只时钟停下时顺手关掉第二只，义务就会从账上消失。

Task142 的修复因此没有去寻找一个更聪明的总分。它把 formal task lifecycle 和 open-obligation registry 分开，让两者各自拥有自己的状态和证据。形式任务的 terminality 由任务范围决定；开放义务的状态由义务自己的终端条件决定。一个终态任务可以带着 `open_obligation_ids`，而开放义务不会反过来把任务改写成 `RUNNING`。

这个拆分看起来像数据结构，实际却改变了这个项目的叙事。系统现在可以说“本轮结束了”，同时继续说“这件事还没有得到想要的结果”。两句话并不矛盾，因为主语不同。

## 三种看似省事、实际危险的做法

第一种做法是开放义务拖住任务。只要某个长期目标没有达到，当前任务就不允许 terminal。它的短期好处是没人会忘记那件事，代价却是状态失去区分能力：已经完成范围的工作和仍在等待外部条件的工作被迫共用一个 `RUNNING`。久而久之，团队不再相信“运行中”意味着什么；所有延期、等待、失败和新工作都挤在同一栏。

第二种做法是任务一关，义务就关。看板很干净，历史却断了。没有人能知道为什么当时没有闭合、曾经尝试过几次、哪个证据是不完整的、未来重新开始需要什么前提。下一轮的人只能把旧事重新猜一遍，甚至把已经发生过的失败当成从未发生。

第三种做法是把开放义务改写成“已经解决”，因为代码测试通过、页面可见或回执齐全。Task142 记录的六次 attempt 和零次 validated completion 恰好提醒我们：过程证据可以很完整，目标仍然没有被满足。工程收据证明的是某些文件、状态和边界在某个时间点对得上；它不替外部执行、现实效果或独立接受发言。

这三种做法其实共享同一个错误：它们没有把“任务状态”和“责任状态”当成两个需要分别解释的对象。

## 一个可用的拆分需要保存什么

只说“分开记录”还不够。若要让下一位执行者真正接得住，至少需要保存四类东西。

第一，保存任务的范围和终态理由。读者要知道它完成的是哪一轮、哪些交付已达到、为什么可以停止，而不是只看到一个 `COMPLETED` 字样。第二，保存义务的身份和终端条件。它究竟要等待什么、什么证据才能关闭、什么情况下只能保持开放，不能靠一句“待后续”带过。

第三，保存历史动作与当前动作的区别。历史记录可能曾经允许下一步进行动态准入；Owner 后来决定把外部 Agent 线停放，这并不意味着历史动作从未存在，也不意味着现在可以自动重试。当前动作必须反映当前授权。第四，保存计数、失败和不完整观察。零次验证不是空白，六次尝试也不是六个成功；它们共同决定未来是否有资格继续、需要先补什么证据。

在这个仓库里，这四类记录让“停下”变得有层次：任务可以停在终态，义务可以停在 OPEN，当前阶段可以转向别的生产工作，而所有历史仍然可追溯。停放不是删除，开放也不是失败，更不是默许系统自行恢复。

## 为什么这对写作也重要

生命周期的拆分不只是给工程师看的。它决定了一篇文章能否把复杂项目写得诚实。

如果文章说“点火已经完成”，读者会追问：完成的是工具、一次回归、一个方法阶段，还是某个外部命题？如果文章说“还没有完成”，读者又会问：到底是本轮没有交付，还是外部证据尚未到来？不把任务和义务分开，写作者只能在乐观和自我否定之间摆动。

有了两个时钟，叙述可以更准确：Task142 完成了它关于生命周期、开放义务和正式发布边界的工程范围；`LIVE_EXTERNAL_INVOCATION` 的 validated completion 仍未形成；后续任务可以在不伪造外部成功的前提下，把阶段转入出版生产。文章因此不必把“没有拿到第一次 validated completion”藏起来，也不必让这件事吞掉已经真正完成的生命周期修复。

这也是一个写作上的反例：诚实不是把所有事情都写成“未完成”，而是给每种完成找到正确的主语和证据。完成的东西得到准确的肯定，开放的东西得到准确的保留。

## 停止以后，谁可以重新开始

拆开时钟还有一个实际收益：未来的重启条件可以变得具体。

一个开放义务不应因为它存在，就自动触发下一次执行。它需要自己的 resume capsule，写明冻结基线、历史次数、已知 blocker、未来 Owner 授权和环境前置条件。没有这些条件，系统最多只能告诉后来者“这里仍开放”，不能把开放状态解释成“现在就该跑”。

这条边界尤其重要于外部执行器。Task142 的开放义务没有因为任务终态而被假装关闭；新的 Phase Closure 任务也没有把它偷偷转成 live attempt。当前的决定是 Owner-deferred：以后只有 Owner 明确恢复，并且本机环境先完成准备、安装和 attestation，才有资格重新审查。历史 attempt 被保留，重启权却没有从历史记录中自动生成。

这让系统可以同时避免两种冲动：用“永远运行”掩盖模型没拆开，也用“已经结束”掩盖责任没安排。

## 结尾：好的停止不是把灯全关掉

对这个仓库而言，一个可用的终态不是所有灯都变成绿色，而是每一盏灯的含义都清楚。任务范围的灯可以熄灭，开放义务的灯仍然亮着；它们照亮的是不同的走廊。只要记录能说清楚哪条走廊已经走完、哪条还在等待、下一次开门需要谁授权，停止就不是逃避，而是可恢复的秩序。

Task142 留下的最值得继续使用的经验，不是一个更漂亮的枚举值，而是一个非常朴素的句法：**这项任务已经结束；这项义务仍然开放。** 把两个主语保留下来，系统才不会因为想显得完成而撒谎，也不会因为害怕遗漏而永远不肯停止。
