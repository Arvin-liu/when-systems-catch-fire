# 已合并，却活在过去：公开当前真相为何会滞后 —— 以及它如何被终结

> 一篇解释性文章（原任务 106 · §12，经任务 108 复审修订 · §10）。它不新增任何裁决、证明或实证，只解释一个被真实撞见的现象：一个仓库可以把一项新成果正式合并进 `main`，而它的公开首页、当前结果页与开放问题页仍在讲述合并之前的旧世界。本文同时解释任务 108 如何把这个现象从"一根软绳子"升级为"一条不可伪造的闭环终态链"，并诚实保留任务 106 自身的历史局限。

## 开头：合并了，然后呢

设想一次普通的代码评审。一项任务通过了预注册、对抗验证、独立复核，最终以一次**普通合并（ordinary merge）**进入 `main`。从版本控制的角度看，这件事已经结束：提交历史里多了一个合并节点，分支可以关闭，回执已经写好。

但如果你此刻打开这个仓库的 README，你可能会读到一个停在更早任务上的"当前状态"；打开"当前结果"页，找不到这项刚合并成果的 verdict；打开"开放问题"页，那项其实已经被基准回答过的问题，仍然写着"候选，需先构建参考 oracle"。

合并发生了。公开页却还活在过去。

这不是某个人的疏忽，也不是"文档没跟上"这么轻松。它是这类仓库的一个结构性缝隙：**Git 合并改变的是机器事实的权威状态，而人类可读的当前真相是另一层、需要被显式传播才能同步的表面。** 两层之间没有任何自动齿轮。本文解释这个缝隙从哪来、为什么它比"错别字"严重、任务 106 如何第一次在 CI 里把它卡住，以及任务 108 如何发现那条卡法本身仍是循环的、并用一条不可伪造的终态链把它真正闭合。

## 一、Git 合并 ≠ 公开当前真相

`git merge` 做的是一件事：把一条分支的提交图接进另一条。它非常精确，也只关心提交图。它不知道 README 第三段在说什么，不知道"当前结果"页该不该新增一行，不知道"开放问题"页里那句"需先构建参考 oracle"现在是否已经过时。

换句话说，**合并只负责"机器侧的事实已经改变"，不负责"人类侧的说法已经更新"。** 这两件事在仓库里由不同的文件、不同的作者、不同的节奏承载。机器侧是确定性的：提交、schema、CI。人类侧是叙述性的：README、RESULTS、KNOWLEDGE、HUMAN-READING。

只要这两层之间没有一根被强制的绳子，它们就会自然漂移。合并越快、越频繁，漂移越容易发生——因为每一次合并都在机器侧前进一格，而人类侧的更新往往要等"有空写文档"的那一刻。

任务 106 之前，这根绳子是软的：有一些同步规则写在 `ITERATION.md` 里，但缺少一把能在 CI 里把"已合并却未同步"直接判红的锁。

## 二、任务 106 的卡法，以及它自己的循环

任务 106 第一次把这根绳子变硬：它在 `data/operations/merged-iteration-ledger.jsonl` 里写入每条已合并迭代的"终态"记录，并让 CI 用 `tools/propagation/validate_reconciliation.py` 去比对公开页是否还停在更早的任务上。这把"已合并却未同步"从一句抱怨变成了一次会判红的校验。这是真实的进步。

但任务 106 的回执自己也坦白了一个更深的循环：那条终态记录是在**准备将要被合并的文件时**写下的，而它又必须填入"自己将来被合并后的 merge commit"。一个 PR 不可能在它还没被合并的时候，就诚实地知道它未来的合并提交号。任务 106 因此把这条记录的 `formal_pr_number / exact_reviewed_head / ordinary_merge_commit` 留成了 `null`（在 `merged-iteration-ledger.jsonl` 里它显示为 `PR_OPEN`），再在合并后由回执事后回填。也就是说：卡住"公开页滞后"的那张表，自身却依赖一个它当时无法知道的未来事实。治理上的缝隙从"页面滞后"转移成了"生命周期表自己不知道自己何时真正闭合"。

这正是任务 108 要修正的：不是再写一张更聪明的单表行，而是把"终态"从一行可变记录，拆成两条**不可变、按时间追加**的事件。

## 三、任务 108：从一行可变记录到两条不可变事件

任务 108 把生命周期改为事件溯源（event-sourced）模型，写在 `data/operations/lifecycle-events.jsonl` 与 `tools/propagation/lifecycle_events.py`：

- **`ITERATION_CANDIDATE`（候选事件）**：在内容 PR 合并**之前**提交。它携带任务号、控制提交、前驱终态、基线提交、内容 PR 号、精确评审头、预期终态、预期终端 tag 名、回执分支等全部事实——**但它刻意不包含任何"未来的合并提交号"**。这是打破循环的关键：候选事件承诺未来会发生什么，却不伪造自己还不知道的合并结果。
- **`TERMINALIZATION_PROJECTION`（终端化投影事件）**：在内容 PR 被**普通合并之后**生成。此时内容 PR 号与内容合并提交都已确知，事件才把它们写进去。它绝不会出现在内容合并之前；解析器会拒绝"早于内容合并的终端投影"。
- **`LEGACY_TERMINAL_SUCCESS`（兼容事件）**：为历史终态行（104/105）保留的向后兼容包装，使解析器无需改写旧记录即可判定它们为已终态。

一个任务的真实状态不再由"一条试图知道自己未来的行"决定，而是由"一组有效事件 + 一个不可伪造的标注终端 tag"**推导**出来。原始历史一行不删、不改：任务 106 在 `merged-iteration-ledger.jsonl` 里的 `PR_OPEN` 行被保留为历史候选证据，而推导视图 (`data/operations/derived-lifecycle-view.json`) 只对它做"历史、非当前真相"的解释。

## 四、用标注终端 tag 闭合，而不是用字符串

任务 108 还要求：每个被归为已终态的任务，必须存在一个**标注（annotated）终端 tag**，形如 `ignition/iterations/<n>/terminal-r1`。这个 tag 不是给人类看的装饰，而是证据链的一环：

- 它必须是标注 tag（有 tag 对象），不能是轻量 tag——轻量 tag 没有可独立校验的对象 SHA，无法防止被悄悄移动；
- 它必须指向终端化合并提交，且消息里绑定 `core_receipt_sha256`（即 `TERMINAL_EVIDENCE_CORE.json` 的内容寻址摘要）；
- `TERMINAL_EVIDENCE_CORE.json` 在两次普通合并之后、tag 创建之前写好，包含全部合并、CI、评审与干净克隆事实；
- tag 在创建后要从一个**全新的完整克隆**重新解析验证，解析器（`tools/propagation/tag_validator.py`）还会拒绝：tag 名不合规、指向错误提交、消息缺字段、core 摘要对不上、重复/冲突的终端 tag、以及把非终端化提交当成终端 tag 目标。

于是"已终态"不再是一句写在文件里的自由文本，而是一段可以被机器从干净仓库里重新走通的链：内容合并 → 终端化合并 → 不可变核心证据 → 标注 tag → 全新克隆验证。任何一环缺失或对不上，解析器都以 `INVALID` / `BLOCKED` 失败闭合，而不是默许。

## 五、为什么 `NO_MAP_IMPACT` 这类声明需要计算支撑

任务 104 和 105 都曾声明自己对首页系统图"无影响（NO_MAP_IMPACT）"。这是正确的——它们没有改动系统图那三个受治理源（构件 registry、传播 topology、布局 overlay）和生成器。

但如果"无影响"只是一句写在回执里的自由文本，它就没有重量。下一次有人改动了一个其实会影响地图的文件，却照样抄一句 `NO_MAP_IMPACT`，CI 也会放行——因为它只会比对字符串，不会比对事实。

所以任务 106 把这件事改成了**可计算的**：系统图的"无影响"必须指名它依赖的受治理源集合，并证明这些源的哈希在合并基线上没有变化。一旦任何一个受治理源变了，引擎会独立推导出"有影响"，声明与推导对不上就判红。自由文本从此不够用了；"无影响"必须能经得起重新计算。任务 108 延续同一原则：终端 tag 的"已终态"也必须能经得起从干净克隆重新计算，而不是被作者重复宣称。

## 六、为什么文章不能被悄悄重新生成

索引可以重新生成。一张资产表、一份变更清单，本质是从机器记录里投影出来的——重新算一遍，得到新的一版，合情合理。

文章不行。

文章是叙述，是主张。把它们塞进"重新生成"的管线，等于让一次格式转换悄悄改写仓库对自己"现在做到了哪里"的说法。任务 106 建立了"素材源变更 → 必须重新评审才能恢复 REVIEWED_CURRENT"的闸门；任务 108 没有放松它，只是把闸门所保护的"当前真相"从单表行升级成了事件溯源 + 标注 tag 的推导视图。本文这次的修订，正是走完一遍"标记为 STALE_REVIEW_REQUIRED → 修订 → 真实评审 → 恢复 REVIEWED_CURRENT"的完整流程，而不是被生成器静默改写。

## 七、诚实的边界

任务 108 不声称本仓库从此再也不会出现任何传播缝隙。它声称的是：缝隙不再依赖一张试图预知自己未来的单表行，而依赖一条由不可变事件与可验证 tag 构成的、能从干净仓库重新走通的终态链；并且若这条链断了（CI 缺失、tag 被移动、核心证据摘要对不上），系统会失败闭合，而不是假装没事。任务 106 自身遗留的 `PR_OPEN` 历史行被显式保留为"当时无法知道未来合并"的证据，而非被抹掉重述。未穷尽审查的开放义务仍按 `RESULTS/OPEN-QUESTIONS.md` 处理。

**主张上限：** 本文只解释"已合并成果为何会在公开页滞后"以及"任务 108 如何用事件溯源与标注终端 tag 闭合其循环"，不新增任何科学、数学或实证结论；不声称本仓库已消除所有传播缝隙，只声称现在有了能在 CI 中 fail-closed 地发现、卡住并诚实闭合它们的、不可伪造的终态链。
