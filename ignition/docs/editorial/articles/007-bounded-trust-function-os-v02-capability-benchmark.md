# 边界之内的可信：Function OS v0.2 能力基准告诉我们什么，以及它诚实停在哪里

有一个系统自称"有界符号函数流水线"：解析规格、受限表示、编译、打包、解释执行、抓执行迹、校验、顺序组合、注册表修订与回滚。名字听起来像一套完备的计算主张。但它的实际身份，按任务 105 的预注册基准，是一组**被显式声明为有界**的能力——它自己也说：不是通用证明系统、不是完备安全沙箱、不是成熟生产平台、不是外部真理机。

这不是修辞。当一句话同时许诺"流水线"和"有界"时，真正的治理问题不是"它有多强"，而是"它划的线，经不经得起被推到线上去测"。

## 为什么这值得一篇文章，而不是一张通过清单

在一个由预注册、冻结阈值、独立 oracle 和确定性语料构成的基准里，最容易滑向的失败有两种：一种是把"全过了"当成结论却删掉失败；另一种是把发现的问题藏起来，让修复后的数字替原始数字说话。任务 105 刻意把这两件事分开：原始目标运行（FOS 在 `16f64004`，未修）和修复后运行（仅修一个被识别出的实现缺陷）是**两件分别封存、分别报告**的证据。

这正是本文要处理的张力：一个系统声称有界，你测出来它大部分边界内成立，但原始目标里有一个真实的实现缺陷——这时"可信"到底成立不成立？

## 原始目标：边界大部分站得住，但有一个真实的缺陷

在 479 个确定性案例、三层对抗（参考语义 / 边界对抗 / 状态生命周期）上，原始目标运行给出：

- **失败闭合边界（A3）成立**：被禁止或不支持的结构，零例被悄悄执行（`false_accept_rate = 0.0`）。一个构造若本应被拒，它要么被拒，要么在 N3 编译期就被挡下——它**从未静默地给出错误结果**。这是整份报告里最值得记住的一行。
- **契约执行（A2）成立**：声明的前/后置条件被强制；失败的执行业务**没有**进入成功注册表路径（`registry_contamination_count = 0`）。
- **制品与迹完整性（A4）成立**：对规格、表示、制品、执行记录、哈希的篡改，全部被校验链检出（`mutation_detection_rate = 1.0`）。
- **注册表修订与回滚（A5）成立**：修订与回滚保留可审计、内部一致的历史，不静默改写先前状态。
- **有界顺序组合（A6）成立**：N8 顺序计划在声明的作用域内保持排序、输入、输出、失败传播与可追溯性。

但语义保真（A1）原始目标只到 `0.9372`（阈值 `0.99`）——差的那一块，不是模糊，而是一个**具体、可定位的实现缺陷**：`N2RepresentationEncoder._extract_expressions` 对形如 `result == (x == y)` 的**嵌套相等**后条件，用 `split('==')`（全拆分）而非首个 `==` 拆分，取到了不完整的右端 `(x `，导致执行期 `'(' was never closed` 的 `RUNTIME_ERROR`。这类案例共 25 个，全部是无声失败——但它们失败得**很干净**：系统报错，而不是吐出错误答案。

这里要分清两件事：缺陷是真实的，但它暴露的是"解析器在嵌套相等上脆"，**不是**"系统会静默给出错误值"。失败闭合这条底线，原始目标也是守住的。

## 修复后：缺陷被有界地修掉，保真回到 1.0

按 §7 的纪律，缺陷被单独修掉：只改那一行——`split('==', 1)`——不动其它任何语义；并加了回归测试（`tests/test_n2_robust.py` 的嵌套相等回归类），全套 166 个测试无回归。修复后运行：语义保真 `1.0000`，全部 7 项主张 `SUPPORTED`，`CRITICAL_VIOLATIONS = 0`，整体裁决 `SUPPORTED_WITHIN_BOUNDED_DOMAIN`。

关键不是"修好了所以全过"。关键是**原始目标那 25 个失败没有被删除、没有被改写、没有被平均数淹没**——它们作为 `aa803277` 那次提交里的 `RESULTS.json` 原样封存；修复结果作为另一次提交 `46471183` 单独存在；预注册提交 `5d664686` 是两者共同的祖先，harness 自带的祖先校验确认了这一点。你可以在不信任任何叙述的情况下，把三次提交拉下来自己复算。

## 仍然有界，而不是被宣布万能

任务 105 测的，从来只是 Function OS v0.2 **自己声明过的有界能力**。它明确不测、也不替这些主张背书：

- 通用证明系统——没有测，也没声称。
- 完备安全沙箱——没有测，也没声称生产就绪。
- 外部真理机——没有测，也没声称。

一个有利的基准，**不**能用来推广任何无关的 Pointfire 主张。那 25 个原始失败案例，是"实现缺陷"而非"能力主张缺陷"——它们被修掉了，但修掉的方式是公开、有界、带回归的，不是把问题从报告里抹掉。诚实的负面与空结果，在这份任务里本身就是有效的完成态。

## 回到开头那条线

真正的问题从来不是"Function OS v0.2 是不是万能流水线"——它明确不是。真正的问题是：当一个系统声称有界，我们靠什么让"有界"不只是口号？

答案不是更聪明的宣传，而是一套可被复算的纪律：预注册先于结果、原始与修复分别封存、失败闭合作为硬性覆盖项、独立 oracle 而非自证、确定性语料与干净克隆复现。线划在哪里，就用证据把它钉在哪里——线之内可信，线之处，老老实实停住，并写清楚为什么停。
