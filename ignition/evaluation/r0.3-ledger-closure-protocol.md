# R0.3 Read-Ledger Closure and Final Attestation

R0.3 supersedes R0.2 for read-ledger finalization. R0.2 schemas, validators, fixtures, and receipts remain historical and are not edited by this protocol repair. This protocol records a deterministic repository-local handoff boundary only; it does not establish cognitive inheritance or explain Task182-R2's private `FAIL_READ_LEDGER_INVALID` result.

## Two explicit evidence surfaces

### `CERTIFIED_LEDGER_SCOPE`

The R0.3 read ledger contains:

- all cognitive reads and their content digests;
- all operational executions before `LEDGER_CLOSURE_POINT`;
- finite status observations for those pre-closure executions;
- an entry-derived summary, trial disposition, and closure metadata.

The ledger schema has `ledger_state=OPEN` before closure and requires `ledger_state=PRE_FINAL_VALIDATION_CLOSED` after closure. The closure object binds `closed_entry_count`, `closed_summary`, and the packet manifest SHA256. The finalizer rejects disagreement between those values and the ledger. Closing is one deterministic transition that adds metadata; after that write, no entry, summary, disposition, or ledger byte may change.

### `FINAL_ATTESTATION_SURFACE`

The finalizer/validator invocation and its returned status are outside the certified ledger. This boundary is represented by the required receipt field `final_validator_scope=FINAL_VALIDATOR_OUTSIDE_CERTIFIED_LEDGER_SCOPE`; it is not an unrecorded exception inside the ledger schema. The tool source remains an operational control component, is listed by component ID and source digest in the packet manifest, and cannot be opened by the Successor.

The deterministic wrapper accepts an open ledger, writes its closure metadata once, validates the resulting frozen bytes, and writes a separate `successor-ledger-validation-receipt-r0.3.json`. Re-running it on the same closed ledger and manifest does not append an event or modify the ledger and produces the same receipt bytes. The receipt binds the ledger SHA256, manifest SHA256, R0.3 ledger-schema SHA256, validator component ID and source SHA256, exact task ID, protocol version, status, and both evidence scopes. A changed ledger byte invalidates the existing receipt.

The receipt is generated by the wrapper; the Successor cannot write a PASS value into it or read it. The CLI writes the deterministic receipt to a separate path outside the Successor-visible packet and emits only a finite status code to stdout. On a repeated invocation, the wrapper internally verifies an existing receipt against the current closed ledger and manifest, then returns the attested status without changing either file. It refuses to overwrite a receipt that does not bind the exact current ledger bytes, so an edited closed ledger cannot silently acquire a replacement receipt. The Successor cannot read the receipt bytes. The receipt is a deterministic local attestation, not a cryptographic signature; exact source, packet, ledger, and CI evidence remain separately reviewable.

## Ordering and operational boundary

The Successor records cognitive reads and every in-scope operational execution/status observation before closure. It then invokes the manifest-listed finalizer once and observes only its finite status. The finalizer and receipt occupy `FINAL_ATTESTATION_SURFACE`, so logging them into the ledger would be a protocol error. The receipt is stored outside the Successor-visible allowlist. The Successor may execute and observe status for listed operational components, but may not read their source, the local authorization receipt, or the final validation receipt.

The R0.2 COMMIT guard's staging rule remains independent of cognitive disposition: untracked evidence can fail COMMIT preflight, and staging the declared evidence can pass it. Such pre-closure guard executions and status observations belong in the ledger. Final closure occurs only after the last ledgered guard result and its ledger entry are staged. No post-closure operation may append a ledger row.

Unknown components, case-specific information in operational output, unlisted cognitive content, digest mismatches, and malformed closure metadata fail closed. Protocol contamination remains distinct from bookkeeping/schema invalidity. Reproducing a possible closure defect with synthetic fixtures does not identify the private Task182-R2 ledger's actual invalid condition.
