# 方法、系统与负结果：哪些东西值得保留，哪些必须能被撤回

## 这也是成果，不是交付附注

点火长期积累的一个容易被忽略的成果，是把“怎么知道自己还没有知道”做成了工作对象。状态文件、来源回链、独立角色、失败夹具、反例、退出和 clean publication 并不构成世界真理；它们构成的是一套可重复的认识工程。若这套工程能让错误更早暴露、让争议不被抹平、让版本可以降级，它就有局部价值；若它只生产更多漂亮回执，就会成为另一种自我确认回路。

本篇登记方法、系统、缺陷和反例四类独立成果单元。每个单元都写清楚：它解决什么现实问题、什么可观察、什么证据不能推出、什么失败会迫使它降级。

## 一、方法成果：把认知工作做成可中断的协议

### 状态先行不是官僚格式

现实问题是：一项长程任务常在换 Agent、换对话、远端更新或上下文压缩后继续；如果状态只在人的记忆里，新的执行者会把“用户要求”“当前事实”“上一轮猜测”和“授权”混在一起。

状态先行的最小变量是 `task`、`known_state`、`role`、`input_tip`、`scope`、`terminal_condition` 和 `next_step`。可观察指标是：一个 fresh Agent 只读控制文件和 refs，能否重建当前步骤；能否指出哪些仍是候选；能否在不满足条件时停下。它不能证明任务本身合理，也不能把文件里的一句授权扩大到外部行动。

### 来源先行把“能说什么”写在对象上

每个结果单元应绑定来源路径或来源族、版本/哈希、证据状态、关系（`RETAINS`/`REVISES`/`SUPERSEDES`/`WITHDRAWN`）和 claim ceiling。这样“某报告记录了某说法”“某史料支持某事实”“项目内部提出某机制”不会被压成同一动词。

可观察的成功不是链接很多，而是读者能从命题回到来源，并看到范围、分母、替代解释和缺失项。来源不可取、只有摘要、只剩转述时，状态应降级；不能靠重复引用同一 source family 抬高等级。

### J+ 与 J− 必须互相独立

J+ 负责找支持、结构一致和可复用候选；J− 负责找矛盾、失败、选择偏差、不可识别和过度统一。两条通道都“找到很多”并不等于接受，真正的出口还要经过 owner 或独立人类评审。

ABSTAIN、`NOT_SUPPORTED`、`NOT_IDENTIFIABLE`、`BODY_RECOVERY_BLOCKED` 和 `REVIEW_DISPUTED` 是合法产物，不是流程失败。它们保留了以后升级的入口，也防止系统为了完成表格而伪造确定性。

## 二、系统成果：回执如何改变工程边界

### 私有控制—执行五面闭环

控制面保存意图、当前状态、角色矩阵和精确 tip；执行面把修改限制在结果分支和隔离 worktree；证据面把路径、版本、哈希和状态连起来；恢复面保存阻断、清理、重绑和下一步；出版面只以文件级方式把可发布内容带到 clean base。

这五面解决的是“能否复核这一轮工作”的问题。它不解决“历史人物到底为何行动”“模型是否在现实中有效”“读者是否认同”。`HEAD == tracking == ls-remote == fresh fetch` 只证明一个远端边界在某时刻收口；它不是事实、因果或授权的替身。

### 双层出版：机器完整性与人类长读

机器 registry 的职责是登记独立结果单元、来源、状态、claim ceiling、关系和未决项；人类成果册的职责是解释这些单元怎样相遇、哪里冲突、为何暂时停下。若只发布 registry，读者会得到一堆标签；若只发布 prose，维护者会失去完整覆盖和反向审计。

因此同一单元必须至少有两条边：`registry → canonical narrative` 和 `narrative → provenance/ceiling`。任何只有文件没有单元、只有数字没有命题、只有命题没有边界的对象，都不能算完整成果。

### clean publication 是治理边界

R2 最终出版从 fresh `origin/main` 建立 publication 分支，只搬入 `results-book/**`、根 README 和确有必要的安全依赖；不 merge、不 cherry-pick R1/R2 的几百个历史提交。这样历史工程、临时回执和研究源库不会无意变成 publication 依赖。

这条边界的代价是：未随出版分支带入的源路径必须写成 provenance-only，不能留下假装可点击的断链；必要的事实背景要嵌入成果册并标出来源层级，而不是把整座历史仓库搬进来。

## 三、负结果：方法怎样失败

### 错误模型也能收敛

如果目标函数错误、输入语料有系统偏差、编码把“同源重复”当成独立样本，或者所有审查者都共享同一提示，J+、J− 和 N 仍可能反复得到稳定状态。这是点火最重要的负结果之一：收敛证明规则内一致，不证明对象外正确。

触发动作是换 source family、引入独立 reviewer、保留反例、检查数据生成过程和降低 claim ceiling；不是增加更多同源迭代。

### 计数增长会制造成果幻觉

516 个函数、案例表的历史数量和 1329 条 GetNote projection 都可能让人误以为“条目越多，知识越多”。去重、主题重叠、版本迁移、同源转述和缺失正文会让行数远大于独立证据数。一个结果单元只有在能独立修订、具有不同命题和明确关系时才应进入 registry；否则是召回索引或 provenance 记录。

### receipt 会冒充现实

绿色 CI、Pages 可访问、哈希一致、fresh fetch 成功，容易让团队产生“系统已被证明”的心理闭环。正确的三栏是：

- **本地/远端工程事实**：文件、commit、测试和部署表面是否一致；
- **语义/证据事实**：命题、来源、反例和测量是否足够；
- **外部/人类接受**：历史核验、独立复现、owner review 和社会结果是否发生。

三栏不能互换；缺一栏就把终态写成残余或待审。

### 起源不可恢复时，空白比漂亮解释更诚实

最早“转身”概念的仓库命中是同步记录，不是对话原点；Q27 旧稿只有本机路径与哈希回执；GetNote 还有 6 个 body recovery blocked。正确做法是写 `EARLIEST_PROVABLE`、`NOT_FULLY_RECOVERED` 或 `BODY_RECOVERY_BLOCKED`，并说明能证明的最远位置。

禁止把后来的成熟定义倒灌到早期文件，禁止把文件修改时间当思想起源，禁止为了让谱系完整而补写“当时用户想表达的内容”。

### 不可识别不是半个支持

如果多个祖先组合、历史过程或心理解释产生同一观测，应该登记候选集、等效关系和下一项信息增益；不能挑一个最符合当前框架的答案。华北大旱原型的总判定 `NOT_IDENTIFIABLE_FOR_UNIQUE_ORIGIN` 就是可读例子：它仍然有研究价值，但不产生唯一因果起源。

## 四、缺陷处理与撤回规则

缺陷优先级不是由“看起来难不难”决定，而由它是否会把内部证据伪装成外部事实决定。以下缺陷一旦发现，不能只在 issue 里提及，必须改变状态或出版内容：

1. 来源路径指向不存在或未授权的私密正文：删除可点击假链，改为 provenance-only，并降级；
2. 计数口径与原始 manifest 不一致：冻结旧数，写 reconciliation，不静默覆盖；
3. 结果被同源重复或模型转述支撑：合并 registry 单元，保留变体在审计层；
4. 新反例击穿核心必要条件：把 `current_best` 改为 `CONTESTED`、`REVISES` 或 `WITHDRAWN`；
5. 机器结果包含私密原文、token、本机路径或过度精细的可重识别信息：停止出版、脱敏、重新 fresh review；
6. 独立 red-team 发现正文与 registry 不相符：先修复覆盖关系，再重新审查，不能只改终态文字。

## 五、反例作为持续维护的测试夹具

成果册必须持续运行五类反例：

- **不燃**：方案清楚、退出存在，却长期无人认领；
- **惯性运行**：没有主动认同但靠便利、惩罚或网络效应运行；
- **预测相反**：点火语言预测失效，其他机制却稳定解释结果；
- **机制替代**：资源、地理、财政、技术或外部冲击比点火机制更有解释力；
- **识别不可得**：无法知道提议者、应约者、时间、退出成本或结果来源。

这些不是为了证明点火失败，而是为了限制“点火能解释”这句话的含义。一个反例可以只击穿某个局部必要条件，也可以迫使整个结果单元撤回；两者必须分开记录。

## 结论与维护出口

当前最稳固的方法成果是：让状态、来源、反证、退出、版本和出版边界可被下一位执行者重建。当前最重要的系统缺陷是：同一套机器能够很快制造比人类更快的候选，审查、独立来源和现实测量却未必同步增长。

因此以后每个新单元都要同时提交“我认为它是什么”和“什么事实会让我撤回它”。成果册是当前证据、算力、模型和研究方法条件下的最佳版本，不是终极真理；任何方法、系统判断、失败解释或反例边界都可以被未来升级、降级、修订、拆分、合并或撤回。
