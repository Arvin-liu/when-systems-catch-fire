# OpenClaw 案例写作操作手册（完整版）

## 一、案例的本质定位

案例不是例子，不是故事，不是场景描述。案例是函数在现实世界中的**可观测实例**，是因果函数的实证载体。

一个合格的案例必须同时满足三个条件：
1. **可观测性：** 有明确的输入、过程、输出，能从外部观察和验证
2. **因果闭合：** 输入到输出之间存在可追踪的因果链条，不是随机事件
3. **函数可映射：** 能明确对应到某个函数或函数组合，不是孤立的轶事

## 二、案例筛选标准

### 2.1 必须满足的硬条件

**条件一：有明确的因果结构**
- 案例必须包含"因为X，所以Y"的结构
- X和Y之间有明确的机制或路径，不是单纯的相关性
- 机制可以是物理的、心理的、社会的、技术的，但必须可追溯

**条件二：有可观测的边界**
- 案例有明确的时间起点和终点
- 输入变量清晰可识别（不是模糊的"环境因素"）
- 输出变量可测量或可判断（不是主观感受）

**条件三：有可重复性或可推广性**
- 案例不是一次性偶然事件
- 同类场景下可以复现或预期类似结果
- 至少能在理论上指出"在什么条件下会再次发生"

### 2.2 优先级排序

**优先级1：函数验证案例**
- 直接验证某个函数的因果预测
- 有明确的数据支撑（实验数据、统计数据、历史记录）
- 能进行"如果函数成立，应该观察到X；实际观察到了Y"的对照

**优先级2：函数应用案例**
- 展示函数在实际场景中的运作
- 有具体的决策过程和结果
- 能说明"函数如何指导了行动"

**优先级3：函数边界案例**
- 揭示函数的适用范围或失效条件
- 展示"在什么情况下函数不成立"
- 对理解函数的约束条件至关重要

### 2.3 排除标准

**坚决排除的案例类型：**
- 纯轶事：没有因果机制的"我有个朋友..."
- 纯相关：只有数据相关性，没有机制解释
- 纯描述：只说了"发生了什么"，没说"为什么发生"
- 纯主观：完全依赖个人感受，无法外部验证
- 过度复杂：因果链条过长，无法清晰追踪

## 三、案例写作的完整流程

### 步骤1：识别候选案例

**输入来源：**
- 用户提供的笔记、录音、对话片段
- 学术文献中的实验或观察
- 历史事件记录
- 商业案例报道
- 技术文档或工程记录

**识别信号：**
- 文本中包含"因为...所以..."的因果陈述
- 有明确的"输入→过程→输出"结构
- 能提炼出"如果...就..."的条件语句
- 有数据支撑的结论或观察

**操作动作：**
- 扫描文本，标注所有可能的因果片段
- 对每个片段问三个问题：
  1. 这个因果有机制吗？
  2. 这个因果可观测吗？
  3. 这个因果能映射到函数吗？
- 三个问题都答"是"→ 进入候选池
- 任一问题答"否"→ 排除

### 步骤2：提取因果结构

**提取目标：**
- 输入变量（X）：明确、可观测、可量化
- 因果机制（M）：从X到Y的路径
- 输出变量（Y）：明确、可观测、可测量

**提取方法：**
1. **识别因果句：** 找出文本中表达因果关系的句子
   - 典型句式："因为A，所以B"、"A导致B"、"B由A引起"
   - 隐含因果："A之后，B发生了"（需验证是否真因果）

2. **拆解因果链：**
   - 如果是直接因果（A→B），直接提取
   - 如果是间接因果（A→M→B），拆解为两个环节
   - 如果是复合因果（A1+A2→B），识别所有必要输入

3. **明确变量：**
   - 输入变量：必须是可观测的实体或属性
   - 输出变量：必须是可测量的结果或状态
   - 中间变量：如果是关键机制，必须明确

**示例：**
原文："因为睡眠时脑脊液流速加快，所以大脑中的代谢废物被清除。"

提取：
- 输入变量（X）：睡眠状态（脑脊液流速加快）
- 因果机制（M）：脑脊液流动冲刷脑组织
- 输出变量（Y）：代谢废物清除

### 步骤3：验证因果有效性

**验证维度1：机制合理性**
- 这个因果机制在物理/心理/社会层面说得通吗？
- 有没有已知的理论支持？
- 有没有反例或矛盾观察？

**验证维度2：观测可靠性**
- 这个因果是被直接观察到的，还是推断的？
- 观察方法可靠吗？
- 数据来源可信吗？

**验证维度3：边界条件**
- 这个因果在什么条件下成立？
- 有没有已知的例外情况？
- 输入变量的范围是什么？

**验证动作：**
- 对每个候选案例执行Y1统一因果自举元函数判定
- J⁺(x)=1, J⁻(x)=0 → 通过
- J⁺(x)=J⁻(x)=1 → 矛盾，排除
- J⁺(x)=J⁻(x)=0 → 待定，需补充验证

### 步骤4：映射到函数

**映射目标：**
- 找到案例对应的函数（或函数组合）
- 明确案例验证的是函数的哪个部分
- 标注案例对函数的贡献类型

**映射方法：**
1. **检索函数库：** 在点火框架函数表中搜索相关函数
   - 搜索关键词：输入变量、输出变量、因果机制
   - 搜索结果可能有0个、1个或多个

2. **匹配判定：**
   - 如果找到完全匹配的函数 → 案例验证该函数
   - 如果找到部分匹配的函数 → 案例扩展该函数的适用范围
   - 如果没有匹配的函数 → 案例可能暗示新函数

3. **贡献分类：**
   - **验证型案例：** 直接验证已有函数的因果预测
   - **扩展型案例：** 扩展函数的适用条件或边界
   - **反例型案例：** 揭示函数的失效条件
   - **启发型案例：** 暗示新函数的存在

**映射示例：**
案例："睡眠时脑脊液流速加快，代谢废物被清除"

检索：找到函数 N27 "睡眠-脑脊液清洗函数"

匹配：完全匹配

贡献：验证型案例（验证函数的因果机制）

### 步骤5：撰写案例正文

**正文结构（必须包含的五个部分）：**

**1. 背景描述（2-3句）**
- 案例发生的具体场景
- 相关的时间、地点、条件
- 为什么这个案例值得关注

**2. 因果陈述（核心部分，3-5句）**
- 清晰表述"因为X，所以Y"
- 说明X到Y的机制（M）
- 如果是间接因果，拆解为多个步骤

**3. 观测证据（2-4句）**
- 这个因果是如何被观察到的？
- 有什么数据或实验支撑？
- 观察方法的可靠性说明

**4. 边界条件（2-3句）**
- 这个因果在什么条件下成立？
- 有没有已知的例外？
- 输入变量的有效范围

**5. 函数关联（1-2句）**
- 这个案例对应哪个函数？
- 案例对函数的贡献是什么（验证/扩展/反例/启发）？

**写作规范：**
- 每句话都要有信息量，避免空泛描述
- 用主动语态，避免"被观察到"这种被动表达
- 数据和事实要精确，避免"大约"、"可能"这种模糊词
- 长度控制在10-20句，200-400字

### 步骤6：质量检查

**检查清单（必须全部通过）：**

**检查项1：因果清晰度**
- [ ] 能一句话说出"因为什么，所以什么"
- [ ] 因果机制明确，不是黑箱
- [ ] 输入输出变量清晰可识别

**检查项2：可观测性**
- [ ] 案例中的因果能被外部观察验证
- [ ] 不是纯主观感受或推断
- [ ] 有明确的数据或事实支撑

**检查项3：函数映射**
- [ ] 明确对应到某个函数
- [ ] 说明了案例对函数的贡献
- [ ] 映射关系合理，不牵强

**检查项4：完整性**
- [ ] 包含背景、因果、证据、边界、关联五个部分
- [ ] 每个部分都有实质内容
- [ ] 没有遗漏关键信息

**检查项5：可读性**
- [ ] 语言简洁，没有冗余
- [ ] 逻辑清晰，没有跳跃
- [ ] 专业术语使用准确

**检查动作：**
- 对每个案例执行上述检查清单
- 任一检查项未通过 → 修改案例
- 全部通过 → 案例完成

### 步骤7：入库归档

**归档信息：**
- 案例标题（格式："N编号 案例名称"）
- 对应函数编号
- 案例类型（验证型/扩展型/反例型/启发型）
- 创建时间（精确到分钟）
- 来源标注（如果来自特定文献或记录）

**归档动作：**
- 将案例写入"统一案例总表"
- 更新案例总数统计
- 如果是新案例，同步更新相关函数的案例计数

## 四、常见问题与处理方法

### 问题1：因果机制不清楚

**症状：**
- 案例描述了"发生了什么"，但没说"为什么发生"
- 只有相关性，没有因果性

**处理方法：**
- 如果原文没有机制，需要补充学术搜索
- 搜索关键词：输入变量 + 输出变量 + "机制"或"原理"
- 如果搜索后仍找不到机制 → 排除该案例

### 问题2：案例过于复杂

**症状：**
- 因果链条过长（超过3个环节）
- 多个因果交织在一起
- 输入变量过多且相互影响

**处理方法：**
- 拆解案例：提取其中最核心的一个因果链
- 如果无法拆解 → 排除该案例
- 不要试图在一个案例中承载太多信息

### 问题3：找不到对应函数

**症状：**
- 案例因果清晰，但函数表中没有匹配的函数

**处理方法：**
- 检查是否搜索关键词不当，换关键词再搜
- 如果确认没有匹配函数 → 标记为"启发型案例"
- 启发型案例可能暗示新函数，但需谨慎，不要轻易创建新函数

### 问题4：案例与函数矛盾

**症状：**
- 案例显示的因果与函数预测相反
- 案例揭示了函数的失效条件

**处理方法：**
- 首先验证案例的因果是否可靠（执行Y1判定）
- 如果案例可靠 → 标记为"反例型案例"
- 反例型案例非常重要，能帮助界定函数边界

## 五、案例质量等级

**等级1：核心验证案例**
- 有明确实验数据支撑
- 直接验证函数的核心因果
- 可重复性高
- 优先级：最高

**等级2：应用观察案例**
- 来自真实场景的观察
- 展示函数的实际运作
- 数据支撑较弱但逻辑清晰
- 优先级：高

**等级3：边界探索案例**
- 揭示函数的适用范围
- 可能包含例外情况
- 需要进一步验证
- 优先级：中

**等级4：启发暗示案例**
- 暗示新函数的可能性
- 因果不够清晰
- 需要更多证据
- 优先级：低

## 六、与函数写作的协同关系

**案例与函数的关系：**
- 函数是因果的形式化表达
- 案例是因果的实证载体
- 函数需要案例验证，案例需要函数归档

**协同流程：**
1. 先有函数假设 → 搜索验证案例
2. 先有案例观察 → 提炼函数假设
3. 函数和案例相互迭代完善

**协同原则：**
- 不要写孤立的案例（没有对应函数）
- 不要写空洞的函数（没有验证案例）
- 案例和函数的数量要保持合理比例（建议至少1:1）

## 七、OpenClaw 操作指令集

**指令1：从文本中提取候选案例**
```
输入：一段文本（笔记、文献、对话等）
输出：候选案例列表（每个案例包含因果结构提取）
操作：执行步骤1-2
```

**指令2：验证候选案例**
```
输入：候选案例
输出：验证结果（通过/排除/待定）
操作：执行步骤3（Y1判定）
```

**指令3：映射案例到函数**
```
输入：已验证案例
输出：函数映射结果（函数编号+贡献类型）
操作：执行步骤4
```

**指令4：撰写案例正文**
```
输入：已映射案例
输出：完整案例正文（五个部分）
操作：执行步骤5
```

**指令5：质量检查**
```
输入：案例正文
输出：检查结果（通过/需修改）
操作：执行步骤6
```

**指令6：批量处理**
```
输入：文本集合
输出：案例集合（已入库）
操作：依次执行指令1-6
```

## 八、案例写作示例

### 示例1：验证型案例

**标题：** N27 睡眠-脑脊液清洗函数验证案例

**背景：** 长期以来，科学界认为睡眠期间大脑会通过脑脊液流动清除代谢废物，这个机制被称为"glymphatic系统"。

**因果陈述：** 因为睡眠时脑脊液流速加快，所以大脑中的代谢废物被清除。具体机制是：睡眠状态下，脑细胞体积缩小，脑脊液流入空间增大，流速加快，从而冲刷脑组织，带走代谢废物。

**观测证据：** 2024年Nature Neuroscience的研究通过直接测量发现，睡眠和麻醉期间的脑清除率实际上是降低的，而不是增加。这个观测与传统glymphatic假说矛盾。

**边界条件：** 该因果的适用条件存在争议。新的研究显示，睡眠和麻醉期间的脑清除率降低，与传统假说相反。

**函数关联：** 该案例对应N27"睡眠-脑脊液清洗函数"，贡献类型为反例型案例，揭示了函数的争议性。

### 示例2：扩展型案例

**标题：** N120 阿尔法优势函数扩展案例

**背景：** 企业和个人在竞争中寻求超越市场平均水平的收益，这种超额收益被称为"阿尔法优势"。

**因果陈述：** 因为找到供需或价格的错配，确认独特资源，做痛苦取舍，沉淀为经济租，并在优势变舒适前重构下一个阿尔法，所以能持续获得超越市场的收益。

**观测证据：** 多个成功企业的案例显示，它们都经历了这五个步骤：亚马逊早期找到电商零售的供需错配，确认其技术优势，取舍了早期盈利，沉淀为品牌和数据资产，在电商变红海前重构到云计算的新阿尔法。

**边界条件：** 该因果适用于竞争性市场，在垄断或完全竞争市场不适用。五个步骤缺一不可，跳过任何一步都无法持续获得阿尔法。

**函数关联：** 该案例对应N120"阿尔法优势函数"，贡献类型为扩展型案例，具体化了函数的操作步骤。

## 九、常见错误与避免方法

### 错误1：把例子当案例

**症状：**
- 只说了"比如A公司做了B事"，没有因果机制
- 没有说明"因为做了B，所以发生了什么"

**避免方法：**
- 严格检查：案例必须包含"因为...所以..."的结构
- 如果只有例子没有因果 → 不是案例

### 错误2：因果机制模糊

**症状：**
- 只说了"A导致B"，没说"怎么导致"
- 用"影响"、"作用"这种模糊词代替具体机制

**避免方法：**
- 必须明确X到Y的路径
- 如果原文没有机制 → 补充搜索或排除

### 错误3：边界条件缺失

**症状：**
- 没有说明因果在什么条件下成立
- 暗示因果是普遍适用的

**避免方法：**
- 每个案例必须包含边界条件部分
- 如果不知道边界 → 标记"待定"或"需进一步验证"

### 错误4：与函数牵强关联

**症状：**
- 案例和函数的因果不匹配
- 强行把案例归到某个函数

**避免方法：**
- 映射时要诚实，不匹配就不映射
- 如果找不到匹配函数 → 标记为"启发型案例"

## 十、持续改进机制

**改进方向1：提高案例密度**
- 在同一场景下寻找多个案例
- 从不同角度验证同一函数
- 建立案例之间的交叉验证

**改进方向2：深化因果机制**
- 对已有案例，补充更多机制细节
- 通过学术搜索深化理解
- 建立案例与理论的连接

**改进方向3：拓展边界条件**
- 主动寻找函数失效的案例
- 明确函数的适用范围
- 建立边界条件的分类体系

**改进方向4：优化写作质量**
- 定期回顾已写案例，检查质量
- 优化表达，提高可读性
- 建立优秀案例的模板库
