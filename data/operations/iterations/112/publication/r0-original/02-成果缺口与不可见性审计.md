# 成果缺口与不可见性审计

## 1. 审计结论

点火已经积累了大量可追溯材料，但读者仍很难直接回答三件事：哪些是研究认识，哪些是研究基础设施；一项认识现在能说到哪；不同报告里的数字和状态是否属于同一个快照。问题不是简单的“缺少更多文件”，而是成果被分散在历史报告、机器 JSON、旧表、公共 README、运行产物和文章中，且各层的口径没有始终贴着读者可见的结论。

本审计把缺口分为四类：

* **成果缺口**：已有材料还没有形成可以独立支持的认识，或缺少领域证据。
* **证据缺口**：已有主张没有足够的来源、全文、实验目标、oracle、复制或因果识别。
* **可见性缺口**：证据存在，但读者必须跨很多路径、JSON 和历史提交才能理解它。
* **谱系缺口**：同一对象出现多个数字、名称、状态或生成时间，却没有统一快照说明。

最严重的发现是计数快照错位，而不是某个单个文件坏掉：

|对象|公开/人类界面表述|基线机器闭合产物|当前判断|
|---|---:|---:|---|
|函数身份卡|5,663 canonical；3,887 quarantine-pending|7,051 canonical；4,978 explicit quarantine/pending|口径、源范围或生成快照不同；本审计不裁决权威数值|
|非函数断言|17,333 canonical；5,581 quarantine-pending|17,626 canonical；5,801 explicit quarantine/pending|同上；不能用差异证明任一方虚假|
|人类成果记录|`RESULTS/CHRONOLOGY.md` 约 287 个研究/文章/架构/Foundation/迭代记录|仓库 tracked files 3,456；其中多数是数据、卡片、测试、索引或生成资产|文件数不是成果数；287 是人类摘要记录的回收范围|
|旧函数索引|2026-07-09 历史索引写 617 个函数；当前 `统一函数总表` 约 624 个文件|Foundation closure 7,051 canonical identity cards|历史表、原始碎片和 canonical cards 不同层级，不能直接对比|
|旧案例索引|2026-07-09 历史索引写 804 个案例；当前目录约 807 个文件|无等价“真实案例数”闭合口径|案例文件数不能当独立样本量或外部证据量|

这个差异会直接影响第一卷的可信度：如果正文写“点火治理了 7,051 个函数”，读者可能把注册表会计误解为 7,051 个已验证函数；如果正文只写公开页面数字，又会漏掉基线机器产物中的更多身份卡和 quarantine。正确做法是把两种快照并列，给出路径、提交和状态含义，直到正式维护流程统一口径。

## 2. 可见性问题的来源

### 2.1 多种时间轴重叠

仓库同时有第一父级任务时间轴、报告创建时间、机器产物生成时间、公共 README 更新时间、旧表的历史日期和后续恢复提交。一个文件在今天可见，不代表它在当时已被纳入公共结论；一个后续提交可读，也不代表它改变固定基线。尤其是任务 111：基线包含实质研究与第一阶段终端化/证据门控材料，但生命周期视图仍把它保留为 non-terminal/awaiting terminalization。本出版包必须把这种状态写成“研究证据可引用、正式生命周期不提升”。

### 2.2 人类表面与机器表面职责不同，却没有近邻解释

README、RESULTS 和文章适合普通人阅读；`closure-summary.json`、`discovery-coverage.json`、`case-status.json` 和 benchmark artifacts 适合审计。问题不是两种表面并存，而是读者看到一个结论时，通常找不到紧邻它的三句说明：统计对象是什么、生成于哪个提交、结论上限是什么。现在的链接结构要求读者自行完成这一步。

### 2.3 旧资产缺少“是否仍然可说”的入口

早期函数、案例和故事仍有研究价值，但其中同时存在保留、待定、降级、撤回、历史仅供参考、重复和未定义对象。`RESULTS/CORRECTIONS.md` 已提供重要修订，但没有把每一个旧对象与新 claim ceiling 组成一个普通读者可读的连续路径。因此“历史上说过”很容易被误读为“现在仍然主张”。

### 2.4 工程通过容易盖过研究边界

Q32/Q32I 的 48 seeds、2 iterations、zero residue、116/116 local tests，Function OS 修复后的 1.0，Crossref 117/117，OpenAlex 101/116：这些数字都是真实的局部运行结果，但数字的视觉冲击比边界句强。若不在正文同句解释，它们会被读成“系统整体正确”“外部论文内容已核验”或“跨域机制得到证明”。

## 4. 读者的单文件可见性设计

本工程后续的 `点火目前真正知道什么.md` 不是新事实源，而是一个不要求读者点击的“结论—边界”入口。它必须执行四条规则：

1. 每项只写一个可读句子，不用任务号替代认识。
2. 结论和边界相邻出现，避免把限制藏在文末。
3. 对计数冲突、null、撤回和未完成目标，直接写出冲突，而不是用“已完成”覆盖。
4. 最后仍给出来源路径和固定基线，供想深入的读者回溯，但不把回溯作为理解全局的前提。

第一卷则承担另一项工作：把单文件的结论串成连续的认识史。它应该先让读者看到一个人为什么会被跨域相似性吸引，再看到系统如何被失败逼着加上边界，最后承认“能管理自己的证据”与“知道世界的机制”之间仍有一段没有跨过的距离。

## 5. 当前能够补的缺口与不能补的缺口

### 可以在本出版包中补

* 对来源家族、任务/报告/作品和纠正做主题台账。
* 把十个章节所需的证据、反例、冲突版本和 claim ceiling 贴在一起。
* 用连续叙事区分发现、基础设施、实验和维护。
* 把失败、null、撤回、target absent 和数字冲突写入正文。
* 为每项研究认识提供一句边界，降低普通读者的误读成本。
* 让审稿人按章节和具体句型提出修订意见。

### 不能在本出版包中补

* 不能替正式仓库维护者决定 5,663 与 7,051 哪一组是唯一公共权威。
* 不能把没有全文的元数据试验变成论文内容核验。
* 不能为苹果案例凭空创建执行目标、反事实或历史证据。
* 不能把 MCF、PSD、ARN 变成真实因果理论。
* 不能把 Function OS 的 bounded benchmark 变成通用函数操作系统。
* 不能把任务 111 的基线材料提升为正式终态。
* 不能用第一卷篇幅制造原始仓库没有的独立实验样本。

## 6. 建议的正式后续维护动作

这些是审计建议，不在本隔离包中执行：

1. 为 Foundation 的公开计数增加 `scope_commit`、`generated_at`、`dedup_rule`、`quarantine_definition` 四个字段。
2. 让 README 的每组数字链接到同一份带快照 ID 的 machine summary，并明确旧数字仍代表什么历史范围。
3. 为每个公开研究结论增加 `claim_ceiling` 和 `evidence_type` 的人类可读短句。
4. 给 Crossref/OpenAlex 页面固定标注 `metadata-only`、`fulltext` 和 `claim support` 的区别。
5. 给 Function OS benchmark 公开 before/after、raw failure、repair commit 和 bounded scope。
6. 给每个真实案例设置 target presence gate：不存在 target 时只能进入历史/叙事审计。
7. 建立一个按研究问题组织的出版索引，不让任务编号继续承担知识目录功能。

## 7. 审计结束语

点火的主要不可见性不是“成果太少”，而是“成果类型太多、边界太远、读者入口太少”。修复方法不是再添加一层宏大术语，而是让每一个进入正文的句子都能被问三遍：它到底观察到什么？它最多支持什么？还有什么没有被测量或证明？
