# 两张表条目写作标准

> 本文件为正式规范。基于审计报告 `outputs/audit/two-tables-entry-format-audit-20260709.md` 固化。
> 生效时间：2026-07-09。

## 目的

统一函数总表和统一案例总表以后**不再允许自由格式写入**。所有新增函数、案例、扩展注释、pending 项，都必须先通过统一模板整理，再进入正式两张表。

本规范与以下模板配套使用：
- `templates/two-tables/unified-function-entry-template.md`（函数条目模板）
- `templates/two-tables/unified-case-entry-template.md`（案例条目模板）
- `templates/two-tables/getbrain-candidate-output-template.md`（得到大脑候选输出模板）

## 适用对象

适用于：得到大脑、Agent、Codex、人工整理、任何后续碰撞流程。
凡向两张表写入内容者，均须遵守本标准。

## 基本原则

写入两张表之前必须满足：

1. **有明确编号**（Dxxx / Axx / Txx / MF-xxxx / C-xxxx，由 Agent/Codex 入表时分配）；
2. **有一句话定义**（函数：可迁移机制；案例：呈现的结构）；
3. **有机制表达**（函数：公式或机制链；案例：因果链）；
4. **有边界条件**（函数不适用范围；案例不能推出的普遍结论）；
5. **有来源回指**（原始材料 / 碰撞批次 / 审计报告路径）；
6. **有 pending 判断**（明确证据等级与未决项）；
7. **有与已有条目的关系说明**（函数：与已有函数边界；案例：为什么不是已有案例）；
8. **缺失字段必须显式标注"缺失"或"pending"，不得伪造确定结论**。

## 函数条目写作标准

正式函数条目必须包含以下字段：

1. **标题** — `# <id>｜<中文名>`
2. **编号** — id，层级（A/D/T/MF），所属函数族
3. **一句话定义** — 一句话说清该函数描述的可迁移机制
4. **数学表达式或机制表达** — 公式或机制链
5. **变量解释** — 列出每个符号含义
6. **因果链** — cause → effect → temporal_order → counterfactual 四要素或机制步骤
7. **适用条件** — 本函数成立的前提
8. **边界条件** — 不适用/失效的边界
9. **反例 / 不适用情形** — 具体反例或明确写"暂无"
10. **与已有函数关系** — 上位/下位/相邻/易混淆函数及区别
11. **对应案例** — 正向登记至少 1 条或写 pending
12. **来源回指** — 原始笔记/碰撞输入路径
13. **pending 状态** — 明确写 pending 项；若已收敛写"无"
14. **扩展注释** — 补充洞察、跨域复现、指标排名隐性分层等
15. **版本记录** — 日期 + 版本/修订说明 + 收敛状态

各字段说明：
- 标题/编号是定位锚，缺编号不允许入表。
- 一句话定义须描述**可迁移机制**，不是概念解释、不是比喻。
- 机制表达是核心；纯文字叙述须能还原为可复用结构。
- 变量解释须与机制表达中的符号一一对应。
- 因果链须含时间顺序与反事实判断（"若没有 X，则不会 Y"）。
- 适用条件与边界条件成对出现，缺一不可。
- 反例/不适用情形鼓励给出，实在无则写"暂无"，不得留空伪装。
- 与已有函数关系不清时，**只能 pending，不得新增**重复或边界模糊的函数。
- 对应案例须正向登记（案例反向引用函数不等于函数已登记该案例）。
- 来源回指不可省；无来源的函数不得直接入表。
- pending 状态须写明证据等级（已验证 / 跨域复现 / 单材料 pending / 证据不足 pending）。

**重点约束**：
- 函数不是概念解释；函数必须描述**可迁移机制**。
- **没有边界条件的函数不得直接入表**。
- **没有来源回指的函数不得直接入表**。
- 与已有函数关系不清时，只能 pending，不得新增。

## 案例条目写作标准

正式案例条目必须包含以下字段：

1. **标题** — `# <id>｜<中文名>`
2. **编号** — C-xxxx
3. **一句话概括** — 一句话说清该案例呈现的结构
4. **现实场景** — 具体时间/地点/主体/动作
5. **核心冲突** — 系统压力/机制矛盾
6. **因果链** — 触发 → 机制 → 结果
7. **对应函数** — 至少 1 条函数编号
8. **证据来源** — 原始材料路径/出处
9. **边界条件** — 只说明什么、不能推出什么普遍结论
10. **为什么不是已有案例** — 与既有案例的关键差异
11. **反例 / 不适用情形** — 限制条件或写"暂无"
12. **pending 状态** — 普遍性 pending / 待补证据等
13. **扩展注释** — 补充洞察
14. **版本记录** — 日期 + 收录/修订说明 + 收敛状态

各字段说明：
- 一句话概括须提炼"结构"，不是故事梗概。
- 现实场景是还原锚点，须具体到可核查。
- 核心冲突是案例存在的理由，须写明张力来源。
- 因果链须能对应到具体函数的机制步骤。
- 对应函数是强制字段；案例必须说明它如何触发某个函数。
- 证据来源不可省。
- 边界条件须显式写"不能推出"的普遍结论，防止过度泛化。
- 为什么不是已有案例须给出与既有案例的差异点；确为新案例写关键差异。

**重点约束**：
- 案例不是故事摘要；案例必须说明它**如何触发某个函数**。
- 案例必须写明对应函数。
- **没有对应函数的案例只能作为候选案例或 pending 案例**，不得直接入正式案例表。
- 案例不能从单一材料推出普遍结论（边界条件强制约束）。

## 得到大脑输出要求

得到大脑以后输出**函数候选**时，必须按函数模板输出；输出**案例候选**时，必须按案例模板输出（见 `templates/two-tables/getbrain-candidate-output-template.md`）。

得到大脑**不负责**：
- 最终编号；
- 最终新增判定（是否入表）；
- 修改两张表；
- Git 操作。

得到大脑**负责**：
- 读材料；
- 提机制；
- 提候选函数；
- 提候选案例；
- 提跨域同构；
- 标注证据不足（缺字段显式标"缺失"/"pending"）。

---

## Agent/Codex 整理要求

Agent/Codex 在正式入表前必须按以下顺序执行：

1. **查重** — 比对已有函数/案例，确认非重复；
2. **跑 Ψ₀ 六维判定** — C(x,y) × M(B_n) × I_iso(A,B) × L_meta × G_δ × P_meta；
3. **做函数边界比较** — 与易混淆函数区分，边界不清则 pending；
4. **套统一模板** — 转换为 `unified-function-entry-template.md` / `unified-case-entry-template.md` 结构（含 frontmatter：kind/seq/id/title/source/source_line/link）；
5. **补齐来源回指** — 登记原始材料/碰撞批次/审计报告；
6. **标注 pending** — 写明证据等级；
7. **更新 INDEX** — 同步函数表/案例表 INDEX 与 README 统计；
8. **生成审计** — 记录本次入表判定与依据；
9. **提交 Git** — 提交信息规范化。

**禁止事项**：
- 不得将得到大脑的候选原文直接塞进两张表（须转模板、补齐字段）；
- 不得为了补齐模板字段而编造证据；
- 不得在边界不清时强行新增函数或案例（只能 pending）。

## 迁移策略

- **不做全表一次性格式迁移**。
- 从 **2026-07-09 之后**的新条目开始强制使用模板。
- 旧条目只在每周维护或被再次引用时逐步补齐缺失字段（边界条件/适用条件/反例/对应案例/版本记录）。
- **D595-D599、C-0807-C-0809 暂不立即迁移**；后续如需格式修订，单独开任务处理。
- 不做大规模自动改写，避免破坏已收敛内容与 frontmatter。
