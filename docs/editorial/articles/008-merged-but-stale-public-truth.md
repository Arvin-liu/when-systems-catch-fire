# 已合并，却活在过去：公开当前真相为何会滞后

> 一篇解释性文章（任务 106 · §12）。它不新增任何裁决、证明或实证，只解释一个被真实撞见的现象：一个仓库可以把一项新成果正式合并进 `main`，而它的公开首页、当前结果页与开放问题页仍在讲述合并之前的旧世界。

## 开头：合并了，然后呢

设想一次普通的代码评审。一项任务通过了预注册、对抗验证、独立复核，最终以一次**普通合并（ordinary merge）**进入 `main`。从版本控制的角度看，这件事已经结束：提交历史里多了一个合并节点，分支可以关闭，回执已经写好。

但如果你此刻打开这个仓库的 README，你可能会读到一个停在更早任务上的"当前状态"；打开"当前结果"页，找不到这项刚合并成果的 verdict；打开"开放问题"页，那项其实已经被基准回答过的问题，仍然写着"候选，需先构建参考 oracle"。

合并发生了。公开页却还活在过去。

这不是某个人的疏忽，也不是"文档没跟上"这么轻松。它是这类仓库的一个结构性缝隙：**Git 合并改变的是机器事实的权威状态，而人类可读的当前真相是另一层、需要被显式传播才能同步的表面。** 两层之间没有任何自动齿轮。本文解释这个缝隙从哪来、为什么它比"错别字"严重、以及这个仓库现在如何让缝隙在出现时被发现、被关闭。

## 一、Git 合并 ≠ 公开当前真相

`git merge` 做的是一件事：把一条分支的提交图接进另一条。它非常精确，也只关心提交图。它不知道 README 第三段在说什么，不知道"当前结果"页该不该新增一行，不知道"开放问题"页里那句"需先构建参考 oracle"现在是否已经过时。

换句话说，**合并只负责"机器侧的事实已经改变"，不负责"人类侧的说法已经更新"。** 这两件事在仓库里由不同的文件、不同的作者、不同的节奏承载。机器侧是确定性的：提交、schema、CI。人类侧是叙述性的：README、RESULTS、KNOWLEDGE、HUMAN-READING。

只要这两层之间没有一根被强制的绳子，它们就会自然漂移。合并越快、越频繁，漂移越容易发生——因为每一次合并都在机器侧前进一格，而人类侧的更新往往要等"有空写文档"的那一刻。

任务 106 之前，这根绳子是软的：有一些同步规则写在 `ITERATION.md` 里，但缺少一把能在 CI 里把"已合并却未同步"直接判红的锁。

## 二、过时的措辞是知识缺陷，不是装修债务

有人会说：这不就是文档落后吗？补一句就行，小问题。

不是。

当一个公开页面声称某项基准"仍是未来候选"，而该基准其实已经执行并有了 verdict，这个页面就**在积极地误导读者**。读者如果基于这个页面做判断——比如认为"这个仓库还没验证过 Function OS"——他得到的不是"少了一条信息"，而是"一条与事实相反的信息"。信息的缺失尚可补救；错误的当前状态会主动把人带偏。

更危险的是，这类错误不会自己暴露。代码能编译、测试能通过、Pages 能渲染——页面照常显示，只是显示的内容是旧的。所以它不是装修债务（难看但不害人），而是**知识缺陷**：它让仓库对自己"现在做到了哪里"这个描述，失去了诚实。对于一个以"保存来源、分离命题与证据、允许结论被修订"为内核的仓库，这种缺陷直接削弱它的立身之本。

## 三、为什么 `NO_MAP_IMPACT` 这类声明需要计算支撑

任务 104 和 105 都曾声明自己对首页系统图"无影响（NO_MAP_IMPACT）"。这是正确的——它们没有改动系统图那三个受治理源（构件 registry、传播 topology、布局 overlay）和生成器。

但如果"无影响"只是一句写在回执里的自由文本，它就没有重量。下一次有人改动了一个其实会影响地图的文件，却照样抄一句 `NO_MAP_IMPACT`，CI 也会放行——因为它只会比对字符串，不会比对事实。

所以任务 106 把这件事改成了**可计算的**：系统图的"无影响"必须指名它依赖的受治理源集合，并证明这些源的哈希在合并基线上没有变化。一旦任何一个受治理源变了，引擎会独立推导出"有影响"，声明与推导对不上就判红。自由文本从此不够用了；"无影响"必须能经得起重新计算。

这背后的原则更一般：**任何"没有影响"的声明，都必须能被机器重新验证，而不是被作者重复宣称。** 否则它只是一句不会被反驳的口号。

## 四、为什么文章不能被悄悄重新生成

索引可以重新生成。一张资产表、一份变更清单，本质是从机器记录里投影出来的——重新算一遍，得到新的一版，合情合理。

文章不行。

一篇编辑文章是经过人组织过的叙事：它选了哪个张力开头，把哪些资产串成一条论证，在哪里显式区分"当前 / 历史 / 开放"。如果它依赖的某个源材料发生了变化（例如某项基准的 verdict 从"部分支持"变成"有界域内支持"），这篇文章要么需要被重新审稿，要么需要被显式标记为"待复审"。绝不能让一个生成器默默改写它的正文，然后把它悄悄恢复成"当前"状态——那等于用自动摘要冒充了编辑判断。

任务 106 为此给每篇文章配了一份机器可读的源清单（source manifest）：记录它依赖哪些源、这些源的哈希、上次审稿的提交、审稿证据，以及它的编辑状态（当前 / 待复审 / 复审中 / 已复审当前 / 已退役）。当一个材料源发生变化，CI 会要求文章离开"当前"状态，除非附带新的审稿证据。文章的意义在于它被人认真读过、组织过；这条线不能被自动化悄悄抹平。

## 五、仓库现在如何发现并关闭传播缝隙

任务 106 把"合并后真相传播"做成了一套可执行的、fail-closed 的基础设施，而不是一份靠自觉的清单：

- **规范化合并迭代台账（ledger）**：每一次被远端验证为已合并的迭代，作为一条带证据字段的记录进入一个追加式的台账。只有终端、远端验证过的记录，才能被用来声称"某项工作已完成"。
- **可计算的 impact 引擎**：对九个面（机器记录、参考表面、编辑文章、系统图、当前公开措辞、开放问题、项目状态、证据程序、成熟度/处置）独立推导"有影响 / 无影响（已证明）/ 待复审"，声明与推导必须一致。
- **确定性当前真相投影**：从台账的终端记录派生出"现在项目到底到了哪里"，并且两次连续生成必须字节一致——任何手工编辑都会被下一轮生成抓住。
- **fail-closed 验证器**：把十二类"已合并却未同步"的失败模式写成断言，非零退出，接入普通 PR 的 CI。正式合并之前，缝隙会被卡住。

关键点在于"fail closed"：当机器发现公开说法与已合并事实矛盾时，它不让合并通过，而不是给一句警告然后放行。传播缝隙因此从"靠人记得补"变成"不补就红"。

## 六、什么仍然必须依赖人的编辑判断

自动化能抓住"说法与事实不一致"，能强制"无影响必须可计算"，能阻止"文章被悄悄改写"。但它做不了一件事：**决定一篇文章该怎么重写，才能既诚实又可读。**

当一项成果的 verdict 需要被重新措辞、当"有界域内可信"这种边界需要被讲清楚而不夸大、当一篇旧文章该退役还是该更新——这些是编辑判断，不是机器能代劳的。任务 106 刻意把自动生成的范围限制在"事实表头、结果索引、当前状态块、过期标记"这类机械投影上，把文章正文的意义留在人工审稿之后。

这也是为什么文章有"待复审"状态，却没有"自动变新"状态。机器可以标记哪里旧了，但把旧变新，仍然是一个人的动作。
