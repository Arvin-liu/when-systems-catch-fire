# 006 反方审查结果

## 审查规则

本阶段不再收集支持性摘要，而是逐项问：如果该主张是错的，哪一项可观察证据会先暴露？每个检查都标明“未推翻”“降级”或“仍未解决”。所有数值来自锁定 CSV、独立脚本输出或完整正文／公开附录定位。

## METR 主结果

### 1. 处理前任务难度是否已经失衡？

用 `predicted_time_no_ai` 和 `predicted_time_ai_allowed` 两个随机前预测字段检查 AI 允许与不允许组：

- 无 AI 预测均值：对照 106.181818 分钟，AI 允许 116.058824 分钟；均值差 9.877005，等方差 t 检验 p≈0.294。
- AI 允许预测均值：对照 82.781818 分钟，AI 允许 87.132353 分钟；均值差 4.350535，p≈0.562。

没有发现足以解释主结果的明显处理前预测失衡。这个检查不能证明任务随机化完美，也不能消除 16 名开发者重复观测和任务提交选择；它只说明“主结果完全由已知事前预测差异制造”的反方解释未被数据支持。

### 2. 是否只有审查时间填补制造了减速？

主结果 `+18.84%`。独立脚本的初始实现时间结果约 `+19.83%`，完整 post-review 案例约 `+20.12%`；论文所述两个极端填补方向得到约 `+22.94%` 和 `+14.20%`。这些都保持正方向，所以“审查时间填补单独制造正结果”未被支持。

但当前 CSV 只有 16 个 post-review 缺失，论文正文写 27 个未审查 issue。极端填补只能说明在已知 CSV 上的范围，不足以消解论文—数据版本差异。该反方点状态为：`NOT_OVERTURNED_BUT_UNRESOLVED`。

### 3. 开发者固定效应是否改变结论？

加入 `C(dev_id)` 并按开发者聚类后估计约 `+14.93%`，95% 区间约 `[-3.97%, +37.54%]`。方向仍为正，但精度不足。故结论从“点估计正”降级为“点估计在多种规格下仍正、开发者级不确定性不可忽略”，不能写成高精度稳定效应。

### 4. 越界字段是否改变异质性？

`external_resource_needs_1_to_3` 有一行值为 5。排除该行后主回归 `+18.84% → +19.08%`，主方向不变；但该字段的解释性分组应视为数据质量受限。异质性结果的交互 p≈0.334，本来就不足以支持强断言，越界值进一步降低上限。状态：`MAIN_DIRECTION_NOT_OVERTURNED; HETEROGENEITY_DOWNGRADED`。

### 5. 论文与当前数据版本是否完全一致？

不是。METR 站点 PDF（50 页）和当前 arXiv PDF（51 页）都写 27 个未审查 issue；精确仓库 commit 的 CSV 只有 16 个 post-review 缺失。仓库在 2025-07-19／21 同步过数据，2026-02-23 的控制 commit 只改 README 符号，无法从现有公开历史恢复论文所说的 27 行映射。主回归能复现，但“数据版本完全等同论文样本”不能确认。状态：`SOURCE_VERSION_DISCREPANCY_REMAINS`。

## Microsoft 竞争结果

### 6. `+26.08%` 是否等于所有开发者的直接处理效果？

否。正文 Table 3 的 pooled W-IV 是三项企业实验的 weekly pull requests 精度加权平均；其解释是采用者 LATE，且访问分配与实际采用不一致。公开附录 Table 5 的早期窗口 pooled ITT 为 `+4.66% (SE 3.56%)`，对应 IV 为 `+20.16% (SE 14.37%)`。这不一定否定作者的首选 W-IV，但证明“访问邀请的 ITT”和“采用者的加权 LATE”是不同 estimand。

### 7. 质量是否被任务数掩盖？

不能从论文得到“质量不变”的总命题。Microsoft approval rate 代理的加权 IV 方向为正，但评论、冲突和 PR 完成时间不显著；Accenture build success rate 的加权 IV 为负。三个企业只有三个环境，而且附录明确说设计与企业工作流差异不能系统识别。状态：`PRODUCTIVITY_PROXY_SUPPORTED; QUALITY_GENERALIZATION_NOT_SUPPORTED`。

### 8. 原始数据是否可继续重算？

公开网页提供 replication files 入口，但要求同意复现政策并填写个人／机构／邮箱字段；本轮未提交表单，且不能将受限数据复制到本分支。故 Microsoft 子任务保留为有凭据的阻断，不用论文表格冒充重算。

## GitHub 竞争结果

### 9. `55.8%` 是否为随机分配全体的无条件结果？

否。95 人被随机分成 45 treatment、50 control，但只有两组各 35 人完成任务；主要时间比较条件化于 70 名完成者。完成率差异只有 7 个百分点，95% 区间 `[-0.11, 0.25]`，未排除完成选择影响。对未完成者的时间没有完整可比观测，因此无法从正文重建全体 95 人的时间 estimand。

### 10. GitHub 是否测了代码质量、返工和维护？

没有。12 项测试提供了固定成功标准，但论文 p.8 明确把代码质量、安全和真实项目外推列为未测限制。状态：`SHORT_TASK_TIME_SUPPORTED; QUALITY_AND_MAINTENANCE_NOT_SUPPORTED`。

## 来源依赖的反方审查

- METR 论文、arXiv 版本、METR 仓库和 CMU CSV 不是四次独立复制；CMU 与 METR CSV SHA-256 完全相同。
- METR 2026 更新是同一机构的后续方法反思，能提供选择偏差反方材料，但不能作为早期数据的外部复制。
- Microsoft 与 GitHub 论文的工具和作者／企业生态有重叠，虽然实验样本不同；第一方博客只作上下文。
- 本轮没有找到可在不提交受限表单的情况下运行 Microsoft 原始 developer-week 数据的公开路径。

## challenge 阶段裁定

1. METR 的窄主张——“在锁定公开数据版本和主模型下，AI 允许任务时间估计增加约 19%”——未被反方分析推翻，但必须附带样本、工具、结果定义、数据版本差异和外推限制。
2. METR 的强异质性主张降级为方向性候选；交互不显著、字段缺失和越界值都必须写入最终报告。
3. Microsoft 与 GitHub 的正向结果不构成 METR 的直接反例，METR 也不构成它们的直接反例；它们是不可合并的竞争 estimand。
4. 最终报告不能说“AI 编程生产率已经确定提高／降低”，只能说三类研究在不同任务、工具、依从性和结果层得到方向不同的有界证据。
