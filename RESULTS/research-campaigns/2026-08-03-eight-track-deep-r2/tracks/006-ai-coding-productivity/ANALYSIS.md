# 006 分析阶段：为什么三类 AI 编程实验方向相反

## 分析对象与符号

METR 的公开脚本把 `exp(beta)-1` 命名为 speedup，但 README 明确说明：正值意味着 AI 允许时耗时更长，即 slowdown。本文件统一把正值写成“时间增加／减速”，负值才写成“时间减少／加速”。Microsoft 的百分比是 weekly pull request 产出，GitHub 的百分比是单一标准化任务的完成时间，三者不共享 estimand。

## METR：主模型和重分析

锁定数据为 246 个 issue、16 名开发者，AI 不允许 110、AI 允许 136。官方脚本按处理组均值填补 post-review 缺失，再运行：

```text
log(total_implementation_time)
  ~ ai_treatment + log(predicted_time_no_ai)
```

直接运行官方脚本得到 `+18.8%`，95% 区间为同方差 `[+1.3%, +39.5%]`、HC3 `[+1.3%, +39.4%]`、开发者聚类 `[+1.6%, +39.0%]`。独立脚本的未四舍五入估计为 `+18.8400%`，与官方输出一致。这是本轮唯一声称“实际复算”的核心结果。

### 结果分解

| 分析 | 估计的时间变化 | 95% 区间／备注 |
|---|---:|---|
| 官方主模型，同方差 | +18.84% | +1.26% 至 +39.48% |
| 官方主模型，开发者聚类 | +18.84% | +1.63% 至 +38.96% |
| 只用初始实现时间 | +19.83% | 开发者聚类区间约 -0.46% 至 +44.25% |
| 只保留有 post-review 的 230 个 issue | +20.12% | 开发者聚类区间约 +2.56% 至 +40.68% |
| 极端填补：AI 允许缺失=60 分钟、对照=0 | +22.94% | 论文所述方向之一的独立复核 |
| 极端填补：AI 允许缺失=0、对照=60 分钟 | +14.20% | 论文所述相反方向之一的独立复核 |
| 开发者固定效应、开发者聚类 | +14.93% | 区间约 -3.97% 至 +37.54% |
| 简单均值比值，填补后总时间 | +33.67% | 描述性估计，不是主因果模型 |

这组结果支持“主结果不是审查时间填补或一个回归选项单独制造的”，但不支持把 18.84% 当成精确稳定常数。均值比值明显更大，说明对数回归、预测时间控制、长尾任务和结果尺度会改变数值；开发者固定效应让区间跨过零，说明 16 名开发者的重复观测仍是重要不确定性来源。

### 异质性

在 159 个有两项预先收集字段的 issue 上，按论文 cutoffs 重算交互模型：

- `Prior Task Exposure > 3` 的高暴露组估计约 `+40.91%`，低暴露组约 `+14.11%`；交互项 p≈`0.313`。
- `External Resource Needs <= 2` 的低外部资源需要组估计约 `+35.66%`，高外部资源需要组约 `+8.66%`；交互项 p≈`0.334`。

方向与论文 Figure 7 的文字描述一致，但交互项不显著，且两个字段在前半段 87 个 issue 缺失。因此最稳妥的表述是“熟悉度／外部资源需要是可重复的方向性候选”，不是“已证明 AI 对熟练者有害、对新手有益”。

另有一个 `external_resource_needs_1_to_3=5` 的越界值。排除该行后主模型从 `+18.8400%` 变为 `+19.0801%`，主方向不变；但它提示该字段的编码或字段名存在质量问题，异质性数值不能高于主结果的证据等级。

## 三项竞争实验放在各自 estimand 内

### METR：熟悉大型仓库的任务时间

METR 让有经验开发者把自己原本要做的 issue 提交后随机进入 AI 允许／不允许条件，主结果是 issue 总实现时间。AI 允许不是强制使用，工具形态包括 Cursor 及当时多种模型；结果包含初始 PR 与审查后修订时间。该环境把“理解已有代码、判断 AI 输出、满足高质量审查”放进结果时间，因此更接近维护型任务，但仍没有直接测量长期缺陷、客户价值或安全。

### Microsoft：企业周级产出和采用者 LATE

Microsoft 论文的 `+26.08%` 是 Microsoft、Accenture 和匿名企业三项不同现场设计的 weekly pull requests 的精度加权 W-IV。单位是开发者周，结果分布有大量零；工具访问分配与实际采用不一致，控制组后来获得访问，所以作者用处理分配作工具变量，估计受鼓励而采用者的 LATE。它回答的是“在这些企业工作流和采用者人群中，Copilot 采用与每周 PR 产出如何关联”，不是“一个 issue 完成耗时缩短多少”。

Microsoft 还提供了质量代理：Microsoft 的 approval rate 方向正，但评论、冲突和 PR 完成时间不显著；Accenture 的 build success rate 方向为负。因而“PR 数上升”不能被翻译成“代码质量、返工和维护都没有代价”。论文也明确说三企业只有三个环境，不能系统识别异质性来源。

### GitHub：标准化短任务的完成者时间

GitHub 的 `55.8%` 来自 95 名随机开发者中的 70 名完成者：45 名处理、50 名控制，最后各 35 名完成任务和问卷。任务是 JavaScript HTTP server，完成时间是从仓库创建到第一次提交通过全部 12 项测试。它有很强的结果固定性，但任务单一、时间窗口短，且主要时间分析条件化于完成者；论文没有代码质量、审查、返工或维护指标。因此它不能直接与 METR 的熟悉大型仓库总实现时间相减，也不能替代长期真实项目证据。

## 竞争证据的机制解释

目前支持的不是“一个结果正确、另外两个结果错误”，而是以下五个可检验的分层差异：

1. **结果单位不同。** METR 测时间，GitHub 测单任务时间，Microsoft 测 weekly PR 数。更多 PR 可能来自更快完成，也可能来自任务切分、工作流或试错变化；没有共同分母不能换算。
2. **任务与熟悉度不同。** METR 的仓库长期维护、参与者熟悉，论文报告熟悉度高和外部资源需要低的 issue 减速更大；GitHub 给所有人相同的短任务；Microsoft 面对产品、测试、设计和客户项目等不同工作流。这是方向差异最直接的候选机制。
3. **工具时期与工具形态不同。** GitHub 论文是 2022 年的 Copilot／Codex 标准化补全，Microsoft 是 2022–2023 年 Copilot 现场采用，METR 是 2025 年早期 Cursor 与多模型的开发者工作流。模型能力更强不保证在熟悉复杂仓库上立即节省人时，因为审查、提示、等待和整合成本也会变化。
4. **依从性和选择不同。** METR AI 允许不强制使用；Microsoft 以访问分配作 IV，控制组后期污染，得到采用者 LATE；GitHub 只在完成者上比较时间，且处理组有未完成注册者。因而各研究的“被处理人”不是同一群体。
5. **质量与时间范围不同。** GitHub 未测质量；Microsoft 用审查、评论、冲突和 build success 代理；METR 有部分 post-review 时间但没有长期缺陷或客户结果。速度结果不能单独代表完整软件价值。

## 当前分析判定

`METR_WITHIN_STUDY_DIRECTION`: 主方向已在锁定数据和官方脚本上复算，候选状态为 `SUPPORTED_WITH_SCOPE`，但论文—CSV 的审查计数差异与字段越界值保留到 challenge。

`CROSS_STUDY_SYNTHESIS`: 三项结果是 `CONTEXT_DEPENDENT_COMPETING_ESTIMANDS`。目前没有证据把它们强行合并为一个 AI 编程平均效果；反方审查应重点检查完成者条件化、控制污染、结果分母、任务熟悉度和质量代理，而不是重复搜集更多同源宣传数字。
