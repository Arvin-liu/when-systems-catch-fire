## 可回答问题

在三类不同软件工程任务中，AI 工具对实际完成时间、完成任务数、质量／返工和开发者主观体验的影响分别是什么？METR 的熟悉大型开源仓库任务、Microsoft 的三项企业现场实验与 GitHub 的标准化短任务是否在任务复杂度、开发者经验、工具形态、依从性和指标上可比？

主问题不是“AI 平均提高多少百分比”，而是识别效果方向和异质性条件。每项研究保留自己的 estimand，不做跨研究百分比平均。

## 预注册结果层

1. `METR_task_time`：有经验开源开发者在其熟悉仓库 issue 上的任务完成时间，按原研究的随机分配和可得分析模型重算。
2. `field_task_count`：Microsoft 三项现场实验的任务数／产出指标，分别记录企业、工具、时间窗、样本和异质性。
3. `controlled_completion_time`：GitHub Copilot 标准化 JavaScript 任务的完成时间与最终完成样本。
4. `quality_and_maintenance`：若原研究没有质量、返工、审查或维护指标，明确标记缺失，不能用速度代替。
5. `subjective_experience`：自报更快、满意度和流畅度只作为体验结果，不作为行为生产率的替代。

## 结论上限

最高只能得到“在某种任务、开发者、工具、时间点和结果指标下观察到 X”。不得形成跨研究平均效果、所有程序员的采购建议、长期缺陷／安全／客户价值结论，除非原始研究直接测量并支持它。

## 最可能推翻候选判断的证据

- METR 原始数据或分析代码不能复现其核心估计，或原始处理存在显著随机化／依从性错误；
- METR 的减速只由少数非依从者、任务选择或早期工具版本造成；
- Microsoft 现场实验的任务数结果在完整正文中依赖不可比的定义、选择性报告或质量下降；
- GitHub 55.8% 只在单一简单任务和小完成样本中成立；
- 新的同任务、同工具随机实验显示相反方向，且质量和返工保持不差；
- 不同经验、仓库熟悉度、任务复杂度或工作流阶段的异质性被合并后改变判断。
